# The running engine's `FUN_1800f4310` against B676's recurrence

## Observation

B676's formula is read from a decompile and only ever compared with itself: no value has come from TF2 while it plays.

## Question

Across consecutive draws of moving models, does the running engine's result cube equal `new - (new - old) * exp(-5 * dt)`, clamped to 0..8, with the first draw the state as it stands?

## Prediction

Every hit matches to 0.001 (a float's error at these sizes). Falsified by any hit further off than that with a `dt` above 0.

## Method

TF2 started directly (`docs/memory/start-tf2-directly-and-hijack-for-a-debugger.md`): `-vulkan -insecure`, one `-hijack +playdemo f12`, f12.dem being the parity reference. Cheat Engine's VEH debugger, two Lua logging breakpoints in `engine.dll`, RVAs read on build 11191711's import: `0xf370b`, the only call to `FUN_1800f4310`, and `0xf3710`, its return.

At the call: `rdx` the handle, `*(rcx+0x18) + handle * 0x148` the instance, its 18 cube floats at `+0x18` and its time at `+0x128` (old), and 18 floats at `r8` (new). At the return: 18 floats at `rax` (result), and the instance's cube and time again. `dt` is the time after less the time before. Written to `D:/measure-f12/b676/live.csv`, read by `D:/measure-f12/b676/live.py`. One attempt, as the review asked.

## Control

- The RVA's bytes in the running module must match the import's `E8 00 0C 00 00` call, or the build differs.
- A nonzero count of hits with `dt` above 0 and a move of over 0.01 between old and new, or the match says nothing.
- The instance's own cube after the call must equal the result, the two being read by separate routes.
- `r_lightaverage` read in the console's default state: a run with it off would never reach the call.

## Environment

TF2 build from `version`; this machine, Vulkan, 1280x720, under the machine lock with a self-timed holder.

## Result

TF2 `PatchVersion=11191711`, `f12.dem` playing, 12,000 logged call and return pairs over 69 instances, `D:/measure-f12/b676/live.csv`, `live.py`. The first load of the script logged nothing, a typo of mine (`EDX` where this Lua has `RDX`) that faulted before any row; corrected and loaded again in the one attempt. The breakpoints slow the game, so `dt` is long.

```

hits 11278; first draws 16, worst from state 0.000000; handles 69, busiest [('1421', 451), ('1420', 451), ('1404', 451)]
dt min 0.061768 median 0.077819 max 44.085510; zero dt 0
control: dt>0 and a move over 0.01 on 3487 hits; worst from the recurrence there 0.000002
worst from the recurrence anywhere 0.000002 at ('1377', 600.940552, 601.019287, 0.07873499999993783); worst result vs stored 0.000000
```

**Controls met:** the call's bytes in the running module read `e8 00 0c 00 00`; 3,487 hits had `dt` above 0 and a move over 0.01; the instance's own cube after the call equals the result on every hit. `r_lightaverage` was not read at the console, but the results differ from the state on those hits, so it was on.

**Seen beyond the prediction:** 722 of the 12,000 are handle `0xffff`, no instance: the gate's third test, the state returned as it stands, exact. **Which models draw with no instance was not found.** This project gives every moving model a history.

**Not exercised:** `dt` of 0 (none occurred, the game being slowed below one draw a time step), and the slots: only the cube was logged.

## Verdict

Prediction **confirmed**: the running engine's cube is the recurrence to 0.000002 across 11,262 later draws, and a first draw is the state, exactly, 16 of 16. So B676's cube, its `exp` and its clock are the engine's, measured. The slots' blend remains read, not logged.
