# Measurement 2026-10-26: how much of a face's flex stream a flex reaches, per model (B597)

## Observation

`2026-10-26-b597-face-cache.md`: f12 draws about 5.4 faces a frame. Every one changes every frame, and each uploads its
model's whole stream, six floats per buffer vertex, about 580 KB. Only the slots a flex names can be non-zero
(`FaceFlex.FlexedCorners`, finding 92 section 4).

## Question

For every class model and every face-flexing cosmetic seen on real demos, how many buffer slots can a flex move, and
how far is it from the first such slot to the last? What does a face actually move on a frame (count, span)? The answer
decides between (c1) uploading the first-to-last range and (c2) a compacted stream of only the flexed slots.

## Instrument

`flex-extent <demo> <tick> <seconds> [every]` (`tools/Tf2DemoSalvage.Probe/Probes/FlexExtentProbe.cs`). It drives
`MomentScene.Build` then `Pose`, the path `viewer-census` drives, with the demo's own appearance and faces.
- The static set is `EntityModelSet.FlexedSlotsOf`: the slots the scene itself writes a driven face through.
- "Motion" counts the slots of each `ModelInstance.Flex` holding a non-zero float on that frame.
- **Control:** every in-motion slot must lie inside the static span. It did, for every model ("inside: yes").
- A model whose face is never driven reports motion only. None appeared here: every listed model had a static set.

## Reading

- **The flexed slots cluster.** For a class model, the span from the first flexed slot to the last is 25-55% of the
  buffer. The count of flexed slots is 23-49%. So a ranged upload (c1) sends 1.00-1.46 times what a compacted one (c2)
  would: soldier 1.05, demo 1.13, sniper 1.07, spy 1.11, engineer 1.04, heavy 1.20, medic 1.29, scout 1.46.
- Both routes cut a class face's upload by about half or more. On f12's four classes, c1 is 34.5-49.9% of the stream,
  against 23.7-44.2% for c2. *Arithmetic from the table.*
- **Why they cluster** (*interpolated from our packing*): `EntityModelSet` packs a model's vertices material by material
  (`EntityModels.Packing.cs`). The head, eyes and teeth are a few materials, so they land in a few contiguous runs.
- **The engine has the same shape.** `R_StudioFlexMeshGroup` writes a flex stream only for the mesh groups flagged as
  flexed (`+0xc & 4`, studiorender `0x180011de0`, disassembly; flag meaning *interpolated*), not the whole model.
- **In motion, a face moves fewer slots than its static set** (a resting scout moves 4.1-4.4k of 5.5k). The upload must
  still cover the static set: a slot that stops moving has to be written back to zero.

## Decision taken from it

**(c1), the ranged upload.** It sends at most 1.46 times c2's bytes (scout), and usually 1.04-1.29 times. It needs no
shader change, no new input stream and no structured buffer. It also matches the engine's shape: flex data for the
flexed part of the model only. c2's extra saving, about 0.1-0.3 MB a frame on f12 (arithmetic), would not pay for a
change to the vertex layout every model draw goes through.
