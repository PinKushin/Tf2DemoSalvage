# Measurement 2026-10-26: the face stream kept on the device against uploading it every draw (B597)

## Record (written and committed before the first run)

## Observation

`2026-10-26-b597-constant-ring-and-occlusion.md` (branch `perf/model-pass-constant-ring`, finding 98 section 12): on f12
gummo first person, mode 2, 1280x720, the OpaqueModels pass is 1.14-1.15 ms CPU and its largest span is `Flex`,
0.271-0.281 ms for 171.8 laps and **3.16 MB a frame**. A lap is every model draw's `BindFlex`, null stream or upload, so
the laps are not the uploads. Arithmetic: a TF2 class model's stream is about 27,000 vertices x 24 bytes = ~650 KB, so
3.16 MB is about five full faces a frame, and the span's time is in those few large `Map(WRITE_DISCARD)` + copies.

## Question

(1) Of the faces drawn each frame, how many hold the floats the device already has from their last upload? (2) What does
keeping each face's stream on the device and re-sending it only on a new write (`FaceStreams`, branch
`perf/b597-flex-upload`) take off the flex span, OpaqueModels, the render thread's draw and the frame, and how many MB a
frame does it still upload?

## Engine (read before this record; the reasoning is in finding 98 section 13 and RISKS B597)

`C_BaseFlex::SetupWeights` (`c_baseflex.cpp:1147-1156`) is the engine's per-draw callback and recomputes the weights with
no change test; `R_StudioFlexMeshGroup` (studiorender `0x1800124f0`, disassembly) rebuilds a dynamic flex mesh per mesh
group per draw. No flex LOD exists to apply (shipped strings: `r_flex`, `r_randomflex`; no distance cut). So the change is
an addition above Valve whose output must be identical, and (b) of the brief has nothing to apply.

## Prediction (before the runs)

- **Held fraction:** the stamp changes only on `FlexFor`'s weight-equality miss, and the weights are evaluated at the
  continuous render-frame time, so a moving face changes on most render frames (the delay, `RunFlexDelay`, decays with
  `curtime`; the medic test held only on a second pose at the same time). Resting faces (worn items, other models) never
  change. Predicted: held across frames, `FlexHeld / (FlexHeld + FlexUpload)`, 30-70%; repeats within a frame
  (`FlexRepeat`) at least the monitor-drawn faces.
- **Bytes:** `FlexUpload` bytes a frame fall from 3.16 MB to 0.6-2.0 MB.
- **Flex time:** the four flex spans' CPU, summed over every pass, falls from M's `Flex` (~0.27 ms in
  OpaqueModels) by 0.08-0.22 ms; OpaqueModels by about the same.
- **Render thread draw:** falls by the same amount, inside its spread or near it. **Frame mean:** unchanged within its
  spread (the render thread is not the frame's critical path at ~10 ms).

Falsified per line if the measured value is outside the stated range beyond the run-to-run spread.

## Instrument

`--measure`'s pass ledger and `SubmitSpans` (`c0584951`). On this branch the flex span is four: `Flex` (no face, the
null stream), `FlexHeld` (a face's first draw this frame, its stamp unchanged since an earlier frame: bound, nothing
sent), `FlexRepeat` (a face already drawn this frame — the monitor pass runs before the world, a two-pass model draws
twice, a resting array is shared by instances: nothing sent), `FlexUpload` (mapped, copied, bound; bytes = what was
copied). Each lap is taken at the call site where `BindFlex` returned which it did (B243). In M (`c0584951`) the one
`Flex` span is all of them. **The brief's fraction** — faces unchanged since the previous frame — is
`FlexHeld / (FlexHeld + FlexUpload)`, summed over every pass; the per-draw skip rate is
`(FlexHeld + FlexRepeat) / (FlexHeld + FlexRepeat + FlexUpload)`. Edge: a face released after a frame out of view
uploads again and counts as an upload. Spans are reported per pass and summed, so cost moved from OpaqueModels into
Monitors is visible. Driver worker CPU: finding 100's thread sampler.

## Method

**Deviation from the brief, stated:** both binaries are built on `c0584951`, the first commit of
`perf/model-pass-constant-ring` (the spans instrument only, nothing of the rings or occlusion), because without it there is
no Flex span to report. Release builds, `MSBUILDDISABLENODEREUSE=1`, each 0 warnings:

- **M** = `c0584951` exported to `D:/b597f/M` (every face draw uploads, one shared buffer).
- **B** = this branch's `f1f94056` exported to `D:/b597f/B2` (the face cache, with the held/repeat split; the first
  export `D:/b597f/B` of `e784275c` lacked the split and is not used).

Each run, one viewer, exclusive, through `2026-10-25-render-thread-cpu-vs-gpu/run.ps1` (its quiet gate: no build or test
process, three load samples under 25%; its command: f12 tick 30000, gummo first person, 1280x720,
`--measure 20 +fps_max 0 +mat_queue_mode 2`). **Order M B B M B M M B** (ABBA then its reverse, four each), so a
drift with run order cannot fall on one condition. A run failing the gate or the after-load check (any sample over 25%)
is discarded and repeated at the end, in the same condition. Raw stdout and sampler CSVs in `2026-10-26-b597-face-cache/`.

Reported per condition, as ranges over its runs: Flex span(s) ms and laps and bytes a frame, OpaqueModels CPU, the
passes' CPU sum, `render thread draw`, frame ms, driver worker ms a frame; the change as % of the frame. A difference
counts when it is at least 0.01 ms and the ranges do not overlap.

## Identity (output parity must be exact)

- `FaceFlexRenderTests.Draw_AFaceSequenceThroughTheCache_IsPixelIdenticalToUploadingEveryDraw`: six frames, cache on
  against off, every pixel equal; the stale control shows the cache is live.
- `FaceFlexAnimationDemoTests.FlexWritten_AMedicPlayingAFlexAnimation_ChangesExactlyWhenItsFaceDoes`: the scene's half.
- One extra B run, untimed, with `TF2VIEW_QUEUE_VERIFY=1` (the stamp is in the verifier's hash): must read 0 changed.
  **The verifier has no positive control** (measurements/2026-10-25-b599-three-allocation-sites.md proposes one); a
  missed stamp bump would not show in it, because the floats match at the hand-off and after the draw — the tests above
  are the guard for that.

## Control

(a) Draws per pass equal in M and B (OpaqueModels ~209). (b) Summed over every pass, B's `Flex + FlexHeld + FlexRepeat +
FlexUpload` laps equal M's `Flex` laps (one lap per model draw in both). (c)
1280x720 in every run; 0 skipped, 0 disjoint.

**Every prediction about a saving is falsified; the held fraction was the wrong premise.** On f12 every face drawn
changes every frame: about 5.4 faces a frame, about 580 KB each, all re-sent. The weights are taken at the continuous
render time — the interpolated `m_flexWeight`, the blink and `RunFlexDelay` on `frametime` — and TF2's idle scenes move
the face continuously. The engine recomputes the same way per draw (`c_baseflex.cpp:1147-1156`), so the faces really do
differ frame to frame. The cache is a no-op here: B's flex, OpaqueModels, render-thread and frame ranges all overlap M's.
B's high ends are run 08, the last run, which matches the run-order drift the brief warned of; nothing is attributed to
it. No face was drawn twice in a frame, and the monitor pass drew none.

**What is left is the bytes, not the count.** Each upload is a model's whole stream, yet a flex reaches about 8.1k of
26.9k soldier slots (finding 92 section 4; 398 at rest). See RISKS B597 for the two bit-identical routes.

**Queue safety:** run 09, B with `TF2VIEW_QUEUE_VERIFY=1`, untimed (load before 19 12 12, after 12 13 8). The log
`%LOCALAPPDATA%/Tf2DemoSalvage/viewer-20261026-172429-24032.log` ends `queue verify: 826500 frames checked, 0 changed`
and has no `inputs changed` line. The count is cumulative since the device was made, not just this run's frames, and
the verifier still has no positive control.

**Decision (owner, 2026-10-26, relayed by the lead): revert the face cache** — D236. The bytes work follows in
`2026-10-26-b597-flex-extent.md`.

## Verdict

Falsified on every saving, confirmed on the frame. Held fraction: predicted 30-70%, measured under 1% (`FlexHeld` below
0.05 of 5.4 uploads a frame); `FlexRepeat` never lapped. Bytes: predicted a fall from 3.16 MB to 0.6-2.0 MB, measured
3.131-3.147 MB in B against 3.148-3.155 in M. Flex time: predicted a fall of 0.08-0.22 ms, measured 0.277-0.295 ms in B
against 0.270-0.277 in M (no fall, the ranges overlap). Render thread draw: predicted to fall by the same amount, measured
2.31-2.36 against 2.31-2.33 ms. The prediction that the frame mean would stay inside its spread held (9.51-9.77 against
9.54-9.60 ms). The held-fraction premise was wrong: every face drawn changes every frame, so the cache was a no-op on
f12, and the owner decided to revert it (D236). The remaining cost is the bytes per upload, taken up in
`2026-10-26-b597-flex-extent.md`.

Verdict written 2026-10-29 after the fact from the Result above; the run itself was not repeated.
