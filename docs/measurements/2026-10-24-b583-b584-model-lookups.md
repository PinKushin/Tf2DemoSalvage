# Measurement 2026-10-24: activity lookup by map, and the draw loop's path probes (B584, B583)

**Status: written and committed before the run.** Sections above `## Result` are fixed from here; deviations go under Result.

## Observation

A code read (RISKS B583, B584, 2026-10-24) found two per-frame lookup costs that no timer separates. `SkinnedModel.ForActivity`
scans every merged sequence with an `OrdinalIgnoreCase` compare and runs 2-6 times per player per frame, where the engine
hashes the activity once (`m_ActivityToSequence`). The model draw loop probes string-keyed dictionaries on the model path about
ten times per prop per frame, where the engine holds the model pointer. Both estimates are code-read: B584 ~0.6-1.0 ms, B583
~1.0-1.5 ms.

## Question

How much frame time do the two lookups cost on f12, gummo first person and the empty view, read from the moment-cost stages
(`models`, `pose` and its parts) and the frame mean?

## Prediction

The read estimates are high. B584: the scan is over a player model's few hundred sequences, a few microseconds a call, so
`pose` falls by 0.05-0.3 ms first person. B583: about 1,600 props times ten hashes of a path string is ~16,000 probes, ~0.3-0.8
ms, landing in `models` and `pose place`. Falsified if the combined drop in `models` + `pose` is below the same-build spread
(null result), or above 2.5 ms (the estimate was right after all).

## Method

Two Release builds of the viewer, copied out so both exist at once:

- **A (before)**: `origin/main` `01faad62`. `D:/measure-f12/b583-before/`.
- **B (after)**: this branch with both changes. `D:/measure-f12/b583-after/`.

Timing, interleaved A B B A A B per subject, each one viewer through `run-exclusive.ps1` (exclusive):

- empty view: `TF2VIEW_AUTOPLAY=1 TF2VIEW_VIEWPORT_SIZE=1280x720 TF2VIEW_CAMERA="1613 -2821 154 89 0" <exe>
  D:/measure-f12/f12.dem --tick 30000 --measure 20 +fps_max 0`
- gummo: `TF2VIEW_AUTOPLAY=1 TF2VIEW_VIEWPORT_SIZE=1280x720 <exe> D:/measure-f12/f12.dem --tick 30000 --spectate gummo
  --first-person --measure 20 +fps_max 0`

Quiet gate before each run: three `(Get-CimInstance Win32_Processor).LoadPercentage` samples under 25%, no build of mine
running. Reported: frames, frame mean, `models`, `pose`, and `pose` parts from the moment-cost line.

**No new timer.** Both costs run inside stages already timed where the work runs (`models`, `pose setup`/`anim`, `place`), so a
drop in those stages is carried, not recomputed. A new timer around a single dictionary probe would cost more than the probe.

## Control

- **Same-build spread** of every reported column is stated beside each A-B difference.
- **Ticks advanced** ~1,333 per 20 s window (the instrument counts playback).
- **Equivalence** is held by unit tests (new path equals old scan for every activity of real and synthetic models), not by
  this record.

## Environment

This machine, 1280x720 windowed, shared with other agents.

## Verdict

**Faster, and the prediction held at its low edge.** The `models` + `pose` drop is about 0.3 ms first person (predicted
0.35-1.1), above every same-build spread, far below the 2.5 ms that would have vindicated the code-read estimates (B584
0.6-1.0, B583 1.0-1.5 ms). Both changes were measured together, so the split rests on which stage moved: `setup` −0.11
for B584, `models` −0.11 and the rest of `pose` for B583 (*interpolated* attribution, one build pair).
