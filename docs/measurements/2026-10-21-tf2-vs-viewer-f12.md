# Measurement 2026-10-21: TF2 against the viewer on the same demo, same moment

**Status: PREDICTION REGISTERED, not yet run.** Written before any measurement, as the process requires (see
`docs/measurements/README.md`). The result goes under `## Result`; this section is not edited afterwards.

## Observation

The viewer measures about 65-69 fps on f12 first person (mean frame 14.5-15.3 ms, the fps agents' `--measure` runs). The owner
reports real TF2 at 400-600 fps in pubs, and the only TF2 measurement on record is `cp_badlands` (893 fps in a room, 1135-1236
facing a wall, GPU about 30%), a different map. The lead has been quoting "about 600 against about 67" as the gap. Nobody has
observed TF2 and the viewer on the same demo, tick and view.

## Question

How many frames a second does real TF2 (the shipped client) draw when it plays `tf/f12.dem` at tick 30000, and how many does
the viewer draw for the same demo, the same moment, the same resolution and the same camera? The only TF2 figure on record is
`cp_badlands`, a different map, and a pub figure from the owner ("400-600"); the gap we quote (about 600 against about 67) has
never been paired.

## Hypothesis

H1: the viewer's frame rate on this scene is between a third and a seventh of TF2's, so a ratio of 3x to 7x.
H0 (what would make the standing "9x" claim wrong): the ratio is under 3x, or over 7x.

## Prediction (numbers fixed before the run)

- TF2, `fps_max 0`, `mat_vsync 0`, window focused, first person spectator at the recorder's view, tick 30000 held for 20 s of
  playback: median 250-450 fps (frame 2.2-4.0 ms).
- Viewer, same demo file, same tick, `--first-person`, `--measure 20 +fps_max 0`, steady seconds (first five dropped): 60-80 fps
  (frame 12.5-16.7 ms).
- Empty view (camera looking at the sky) in each: TF2 600-1200 fps, viewer 150-200 fps.

## Falsified if

- TF2's median in the 20 s window is under 150 fps or over 650 fps (the prediction of 250-450 is then wrong by more than half),
- or the viewer's is outside 50-90 fps (our own last measurements said 65-69; outside this means the build or the scene differs
  from what we think),
- or the ratio in first person is under 3x or over 7x (H1 is then false).

## Control

- Run each side twice; the two medians must agree within 15%, or the run is void and repeated.
- The empty-view reading in each client is the floor control: a first-person figure below its own empty-view figure is a mistake.
- Resolution, window state and GPU load recorded for both (below); a mismatch voids the comparison.

## Method

**The observation that answers the question:** frames drawn per second (mean and the spread) in each client, over the same 20
seconds of the same demo starting at tick 30000, from the recorder's own view (f12 is a POV demo of a Medic, so TF2's default
playback view and the viewer's `--first-person` are the same eye), at the same window size, with the frame-rate cap removed.
The empty-view floor is measured the same way with the camera pointed at the sky.

**The demo:** TF2's own `tf/f12.dem` (34,560,994 bytes), not lcor's f12 (a different match on the same map). The viewer plays a
space-free copy made OUT of the game folder (nothing is copied into it).

**Both machines state, before anything else:** the GPU load, the CPU load before and after (the machine lock is held for the
whole session, no other run or build overlaps it), the window's client size in each client.

**TF2 side**
1. Read and record these cvars before changing any, and read them back after restoring: `fps_max`, `mat_vsync`, `cl_showfps`,
   `net_graph`, `mat_queue_mode`, `fov_desired`, `mat_hdr_level`, `r_drawviewmodel`, `demo_timescale`, `host_timescale`.
2. Windowed at the viewer's client size (`mat_setvideomode <w> <h> 1`, size read from the viewer first), `fps_max 0`,
   `mat_vsync 0`, `cl_showfps 2` (shows the averaged rate and its min and max on screen), `demoui` open so the tick is in the
   picture. TF2 has the foreground (`engine_no_focus_sleep` clamps an unfocused client).
3. `playdemo f12`, `demo_gototick 30000 0 0` (forward seek only; TF2 cannot rewind), let it settle 5 s, then take a screenshot
   every 4 s for 20 s (`mcp__tf2__screenshot`); the on-screen average, minimum, maximum and the tick are READ OFF THE PICTURES
   and written into Result with the file names. Repeat the whole playdemo once (second run). Then the sky: `spec_goto`-style
   free camera is not available in a demo, so the empty-view control uses `+left` to turn the view toward the sky or the
   floor-facing wall, whichever the demo allows; if neither can be set exactly, the empty-view figure is reported as not
   measured on this side and says why.
4. Restore the cvars and the video mode, quit TF2 when done.

**Viewer side** (build of current `origin/main`, Debug folder, the build the owner runs; the commit is written in Environment):
`TF2VIEW_AUTOPLAY=1 pwsh run-exclusive.ps1 <exe> <space-free copy> --tick 30000 --first-person --measure 20 +fps_max 0`, twice;
steady seconds (first five dropped) are the figure, with the `--measure` line's mean frame time converted to fps. Empty view:
`TF2VIEW_CAMERA` pointing at the sky as the measure skill describes.

## Control

- The two runs of each client must agree within 15% on the median, or the run is void and repeated.
- The empty-view reading in each client must be at least as high as its own first-person reading; if not, a step is mistaken.
- The pictures prove the tick: the `demoui` tick in each screenshot must be within a few ticks of 30000 and advancing.
- The window sizes must match to the pixel, or the comparison is reported as unpaired.
- **The instrument is asked for something known.** `cl_showfps 2` read off a picture is checked by setting `fps_max 60` for one
  screenshot: it must read about 60, and read the uncapped figure again after `fps_max 0`. (Pausing the demo to check is not
  allowed, because a paused demo wedges RCON.)
- Deviations from this method are recorded under Result, never edited into this section.
