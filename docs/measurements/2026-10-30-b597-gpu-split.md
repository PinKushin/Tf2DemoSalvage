# Measurement 2026-10-30: B597, the opaque models' GPU time split into vertex work and per-draw cost

## Record (written and committed before the first run)

## Observation

`2026-10-25-render-thread-cpu-vs-gpu.md` measured OpaqueModels at 0.83-0.85 ms of GPU time on f12 gummo first person
(1280x720, mode 2) and 0.87 / 0.83 / 0.84-0.87 ms at 640x360 / 1280x720 / 1644x931: flat with pixels, so not pixel-bound.
Its CPU is 1.06-1.08 ms for 209 draws, 421 maps, and 227,000 primitives (non-indexed `Draw`, so about 681,000 vertices
shaded, each skinned). RISKS B597 left it "not yet split into vertex execution vs submission pacing", and that split
decides whether the GPU alone caps a 1 ms frame: if the GPU time is vertex execution, it is a floor no CPU work lowers;
if it is the GPU waiting on CPU submission, lowering CPU submission lowers it too.

## Question

On f12 from tick 30000, gummo first person, 1280x720, `+mat_queue_mode 2`: when every model draw keeps its binds and
state but submits at most 3 vertices (V3), or no draw at all (V0), how much of OpaqueModels' GPU time remains, against
the normal frame (N)? Does the pass's GPU time follow the CPU time that submits it?

## Hypothesis

OpaqueModels' GPU time is a mix: part vertex work (fetch and skin 681,000 vertices, set up 227,000 triangles) and part
per-draw cost (state, binds, the GPU waiting for the CPU to submit the next draw).

## Prediction (before the runs)

Reading the timestamps as the earlier record does: a pass's GPU delta is about max(submission pacing, execution).

- **N** reproduces the earlier record: OpaqueModels GPU 0.80-0.90 ms, CPU 1.00-1.12 ms, 209 draws (the pass may differ
  by a few draws; it is carried from the run, not assumed).
- **V3: OpaqueModels GPU falls to 0.45-0.65 ms**, CPU within 0.10 ms of N (the binds and state remain; only the
  vertex count changes), draws equal to N's, primitives about equal to the draw count (one triangle a draw) against
  N's 227,000.
- **V0: OpaqueModels draws 0, GPU at or above 0.30 ms and no more than V3's plus the N spread** (state binds still run on the CPU, and the
  timestamp delta still includes the GPU waiting on the CPU); CPU falls by the cost of the `Draw` calls only.
- Reading: V3 GPU within 0.10 ms of N means the GPU time is **not** geometry work (pacing-bound: lowering CPU submission
  lowers it); V3 GPU under 0.30 ms means the GPU time is **geometry-bound** (a floor no CPU change lowers); in between is
  mixed, and the split is read off the two numbers. "Geometry work" is everything a 3-vertex draw removes: vertex fetch
  and skinning, triangle setup, rasterisation, and the pixel work of those triangles. The resolution scan (flat from
  640x360 to 1644x931) rules out the pass being pixel-BOUND, not pixel-free, so V3 cannot separate vertex from pixel
  cost and the record does not claim to.

## Falsified if

Any one of:

1. V3's OpaqueModels GPU is within 0.10 ms of N's (the prediction of a mix fails: it is pacing).
2. V3's OpaqueModels GPU is under 0.30 ms (it is geometry-bound).
3. V3's draws differ from N's by more than 3 (the control then changed something beyond the vertex count).
4. V3's pass CPU differs from N's by more than 0.10 ms **and** the `submit spans` split shows the difference outside the
   draw call (a lighter GPU frame also changes buffer-map back-pressure, so a CPU move that sits in the map spans is not
   a broken control).
5. V0's GPU exceeds V3's by more than the spread (max minus min) of the three N runs' OpaqueModels GPU.

*Amendment, 2026-10-30, before any run of the build below: clauses 3 to 5 were tightened or split after two Opus
reviews (V0 against V3 had no tolerance; CPU can move through back-pressure; one clause's scope was ambiguous). Predicted
numbers are unchanged.*

## Instrument

`Render/PassProfiler.cs` as before (per-pass CPU, GPU timestamps, draws, maps, primitives, printed by `--measure`). One
new control, `TF2VIEW_MODEL_VERTS` (`Render/ModelVertexClamp.cs`, unit-tested, sabotaged red): read once at start, caps the
vertices of every `WorldRenderer.DrawModel` batch draw and skips the draw at 0; every bind, state change and map before the
draw still runs. It applies to all `DrawModel` callers, so the viewmodel and translucent model passes move too; they are
read but not claimed. **Model decals are clamped too** (they draw inside the OpaqueModels pass through
`DrawModelDecals`; the Opus review found they were not, and the first build's V0 runs showed it: the pass still issued
draws). **The cloak pass's own draw is clamped too** (both reviews found it was not). **Only a cap of exactly 0 skips a
draw**: under a cap of 3 a batch with no vertices is still drawn, as in the default, so V3's draw count equals N's. The
clamp is wired in tests (`Rendering.Tests`), not only parsed.

## Method

One Release build of this branch's commit, from a `git archive` at `D:/measure-f12/b597-split-src` built `-c Release`
and copied to `D:/measure-f12/b597-split`. Nine runs from the same exe, only the environment differing, behind the
quiet gate (`run.ps1`: no other viewer or build process; three `LoadPercentage` samples under 25%; load sampled after),
under `run-exclusive.ps1`:

`TF2VIEW_AUTOPLAY=1 TF2VIEW_VIEWPORT_SIZE=1280x720 [TF2VIEW_MODEL_VERTS=<n>] <exe> D:/measure-f12/f12.dem --tick 30000 --spectate gummo --first-person --measure 20 +fps_max 0 +mat_queue_mode 2`

Order (counterbalanced so drift does not line up with a condition): N V3 V0, V0 V3 N, N V0 V3. Reading: `summ.ps1`
(the passes block `--measure` prints), the mean of the three runs per condition with their range.

## Control

(a) The clamp took effect: in V3 OpaqueModels' primitives collapse from about 227,000 toward its draw count, and in V0 its
draws read 0; if either does not, the knob is not reaching the draw and nothing is read. (b) N reproduces the earlier
record's OpaqueModels (GPU 0.83-0.85, draws 209) within the earlier spread; if not, the machine or build differs and the
comparison is void. (c) The three N runs agree with each other (the A/A spread) and the V3 effect is larger than it.
(d) Passes the clamp cannot reach (World, Occlusion, Sky3D, Hud) keep their GPU within their own N spread in V3 and V0;
a move there is order or load, and is reported against the OpaqueModels figure. (e) Backbuffer size printed is 1280x720.
(f) VSync is off (`+fps_max 0`).

## Environment

This machine, Windowed, NVIDIA driver, branch `perf/b597-gpu-split` (Release, 0 warnings). The build's commit is
recorded in the Result when the runs start.
