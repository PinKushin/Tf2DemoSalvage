# Measurement 2026-10-22: how TF2 and the viewer use CPU threads on f12, and what 2 cores cost each

**Status: written and committed before the run.** Sections above `## Result` are fixed from here; deviations go under Result.

## Observation

The last pair (`2026-10-22-tf2-vs-viewer-f12.md`) read TF2 at 207 fps mean (194 and 227 per playback) against the viewer's
74.8 fps on f12, first person on gummo, 1280x720. Machine CPU read 40-68% while TF2 played against 14-19% for the viewer, on a
12-thread i5-10600K. The owner, 2026-10-22, thinks the gap is mostly threading: *"modern TF2 on 2 cores at ultra is insane"*; he
expects our time is in what TF2 spreads over threads.

## Question

(A) Over a ~20 s window of f12 first person (same tick region, same settings as the last pair): how many threads does `tf_win64`
keep busy, what does each cost per second and per frame, and which module each thread starts in (engine, client, materialsystem,
shaderapidx9, driver, thread pool)? Which is the game thread and which the render / material-system thread? The same for
`tf2demoview.exe`, like for like.

(B) What fps do TF2 and the viewer hold when restricted to 2 logical processors, against all 12? If TF2 holds most of its fps on
2 cores, threading is not what separates the two; if it collapses, it is.

## Prediction (the owner's hypothesis, stated so it can fail)

- TF2 keeps 3+ threads above 30% of a core; the viewer keeps 1-2.
- TF2 on 2 cores loses more than 30% of its all-core fps; the viewer on 2 cores loses less than 15%.
- Falsified if TF2 on 2 physical cores keeps 85%+ of its fps.

## Method

**Instrument:** `2026-10-22-threads-f12/sample-threads.ps1` samples `Process.Threads` `TotalProcessorTime` once a second for every
thread, and each thread's Win32 start address (`NtQueryInformationThread` class 9) resolved against `Process.Modules`.
`summarize.ps1` takes a window and prints % of one core per thread, and ms per frame given the window's fps. Caveats: CPU time
includes spin-waiting, which is not useful work; per-thread totals are not the per-frame critical path; a start module names
where a thread began, not what it runs (a thread-pool worker runs whatever is queued).

**Order, one machine-lock hold for the whole TF2 session** (`run-exclusive.ps1` holding a sleep while TF2 is up; the viewer runs
take the lock themselves, outside that hold):

1. Instrument control (below).
2. Viewer run A and run B, all cores, sampler running beside each: the command of the last pair
   (`TF2VIEW_AUTOPLAY=1 TF2VIEW_VIEWPORT_SIZE=1280x720 … tf2demoview.exe D:/measure-f12/f12.dem --tick 30000 --spectate gummo
   --first-person --measure 20 +fps_max 0`). Window: the last ~20 s of the sampler series before exit, where the per-second
   samples of `--measure` are steady; frames from the `--measure` report.
3. Viewer on 2 logical processors: same command, `ProcessorAffinity` set as soon as the process appears (load happens on it too),
   mask `0x3` (logical 0 and 1, one physical core's two hyperthreads) and mask `0x5` (logical 0 and 2, two physical cores), one run
   each. The `--measure` mean is the reading.
4. TF2 (launch through `mcp__tf2__launch` only if no client answers): read and record `fps_max`, `mat_vsync`, `cl_showfps`,
   `engine_no_focus_sleep`, `spec_autodirector`, `sv_allow_wait_command`; set `fps_max 0`, `mat_vsync 0`, `engine_no_focus_sleep 0`,
   `cl_showfps 2`. `playdemo f12`, `demo_gototick 30000 0 0`, `spec_player gummo; spec_mode 4`. One screenshot to prove the camera.
   Then the sampler for ~25 s with no TF2 call inside it; a screenshot just before and just after the window gives the fps for
   ms-per-frame. Then affinity: all cores, `0x3`, `0x5`, back to all; under each, 3 screenshot readings ~5 s apart after ~5 s to
   settle, foreground checked at each (`tf_win64`). The demo may need a re-seek to stay in the region; recorded if so.
5. Restore every ConVar and read back; restore affinity to all; quit TF2. Machine load
   (`(Get-CimInstance Win32_Processor).LoadPercentage`) before and after each run.

## Control

- **Instrument:** a pwsh process spinning on 1 thread must read ~100% of a core on one thread; one spinning 4 threads must read
  ~4 threads at ~100%; their start module must resolve to something (not all `unknown`).
- **Topology:** two spinning threads pinned to `0x3` against `0x5`, iterations counted: if `0x3` is one physical core, it delivers
  clearly fewer iterations than `0x5` (hyperthreads share a core). This decides which mask is which, not an assumption.
- **Viewer repeat:** runs A and B within 15% on mean fps, else run-to-run spread is reported and the 2-core verdict for the viewer
  is weakened accordingly.
- **TF2:** a reading counts only if `tf_win64` was foreground and the picture is gummo's first person.

## Environment

i5-10600K (6 cores, 12 logical), RTX 3060, desktop 1920x1080. Viewer: `origin/main` `60afd9b6`, Debug, as the owner runs it. TF2:
shipped client, the owner's config, windowed 1280x720. Owner home and has said go.

## Result

Raw outputs are in `2026-10-22-threads-f12/`: one sampler CSV per run (`viewer-*.csv`, `tf2-*.csv`, `control-spin*.csv`), the
viewer's whole `--measure` reports (`viewer-*.txt`), and `tf2-fps-readings.png`, the `cl_showfps 2` overlay cropped out of all 16
TF2 screenshots in the order they were taken. The scripts are next to them. The machine lock was held from 19:16:43 until the end.

### Controls

- **Instrument** (run again under the lock, load 29%): a pwsh process spinning on 1 thread read **98.8%** of a core on one thread.
  The same with 4 threads read **4 threads at 81-86%**, and every other thread read 0.0%. Start addresses resolve (every managed
  thread starts at `coreclr.dll+0xd22f0`). The instrument counts busy threads correctly. It reads about 15% low on a 4-thread
  spinner, because the window takes in the threads' start.
- **Topology** was read from the OS (`topology.ps1`, `GetLogicalProcessorInformationEx`): physical core n is the logical mask
  `0x3 << 2n`. **`0x3` is one physical core's two hyperthreads, and `0x5` is two physical cores.** The spinner gave the same answer:
  2 spinners did 9.1-10.2 M iterations on the hyperthread pairs `0x3`/`0xC`/`0x30`, against 16.8-17.9 M on the cross-core masks
  `0x5`/`0xA`/`0x14`. A first run of that control (before the lock) overlapped another agent's viewer run and is discarded.
- **Viewer repeat:** run A gave 73.8 fps and run B gave 56.2 fps, **24% apart: the 15% control fails.** Viewer figures carry that
  spread. The machine was in use during the runs (floorp, claude and Antigravity together took ~0.5 core, and load before the runs
  was 11-30%).

**TF2.** One playback, with the affinity switched on the running process. Each reading came 3-6 s after a switch, with `tf_win64`
foreground at every switch. From 19:45:30 the conditions alternate (all, 0x5, all, 0x3, all, 0x5), so scene drift falls on all
three conditions alike.

| condition | counted readings (fps) | mean | of all-core |
|---|---|---:|---:|
| all 12 | 235, 150, 158, 223, 144, 208 | **186** | 100% |
| `0x5`, 2 physical cores | 91, 105, 105, 103, 75 | **96** | **51%** |
| `0x3`, 1 core / 2 hyperthreads | 122, 100 | **111** | 60% (2 readings) |

Excluded: 113 (`0x3`, gummo dead in the death cam), 300 (all, the round-win screen), and 46 (all, seconds after the re-seek, with
Antigravity in the foreground). The per-thread picture under restriction (`tf2-2phys.csv`, `tf2-1core2ht.csv`, 11 s each) keeps the
same three busy threads at main 55%, driver 40% and `CThread` 39%: 137% of 200% on `0x5`, and 142% on `0x3`. While those windows

### Deviations from the Method

1. The viewer runs went straight to the exe while this session held the lock (run-exclusive would have waited on that lock).
   `TF2VIEW_VIEWPORT_SIZE=1280x720` was set, as in the last pair.
2. The viewer's 2-core affinity was set 180 s in rather than "as soon as it appears", so loading would not run on 2 cores. Its
   record line says so.
3. TF2 wandered out of the tick region. Three rounds went by, including the round-win screen, and a re-seek followed at
   19:45. Readings are from several parts of the match, not one 20 s region, which is why the later readings alternate conditions.
4. The TF2 window fps for ms/frame is the mean of the screenshots before and after the window (235 and 150), not a frame count.
   `cl_showfps` gives no count.
5. Thread names (`GetThreadDescription`) came back `?` for TF2. The viewer runs went before the name column was added. So neither
   side's threads are named beyond their start module.
6. TF2 was focused once by `AppActivate` (19:45:30) after the Antigravity window took the foreground.
7. ConVars read before: `fps_max 0`, `mat_vsync 0`, `cl_showfps 0`, `engine_no_focus_sleep 50`, `spec_autodirector 1`,
   `sv_allow_wait_command 1`. All were restored and read back with the same values. Affinity was restored to `0xFFF` and read back,
   and TF2 was quit.

### Unverified

- **Which TF2 thread is the queued material system.** The busy `tier0.dll+0x2e060` thread is a `CThread` started through tier0. It
  matches finding 98's queued material-system thread, but a start address cannot name it. A stack sample (Ghidra or a debugger
  attach) would.
- What the viewer's 30-45% managed thread is: particles, the loader, or the GC. Its name was not read.
- Whether the 0x3 result being higher than 0x5 is real. There are only two 0x3 readings, against five scattered 0x5 readings.

## Verdict

**Prediction partly confirmed, partly falsified.**

- **Confirmed: TF2 is threaded and the viewer mostly is not.** TF2 keeps **3 threads near or above 70%** of a core (main 95%, D3D9
  driver 71%, a tier0 `CThread` 70%): 2.4 cores in total, 4.9 ms a frame on the main thread. In steady playback the viewer keeps
  **one** (main 96%, 13.1 ms a frame), plus a driver thread at 14% and a 30-36% managed thread.
- **Confirmed: TF2 collapses on 2 cores.** It holds **51%** of its fps on 2 physical cores (186 to 96) and ~60% on one hyperthreaded
  core. That is far below the 85% that would have falsified the owner's view, so TF2 does depend on its threads.
- **Falsified: "the viewer loses less than 15% on 2 cores".** It loses as much as TF2 does (63-71% kept on `0x5`, 51-58% on `0x3`).
  That is nearly as large as TF2's loss, from a process that uses only 1.5-1.6 cores. The viewer is also sensitive to having
  spare cores.

**What it implies for the plan (candidates only, no code recommended).** TF2's frame runs on a main thread at 4.9 ms, with two helpers
carrying 3.6-3.7 ms each in parallel: the driver's own worker, and what is very probably the queued material system (finding 98,
D228). Even TF2's *main thread alone* (4.9 ms) is 2.7x shorter than the viewer's main thread (13.1 ms). So threading accounts for
part of the gap, roughly the ~3.6 ms TF2 moves off its main thread. The larger part is that the viewer's single main thread does
~13 ms of work where TF2's does ~5. Candidates to look at, in the order the numbers point:

1. What the viewer's main thread spends 13 ms on. `--measure` already splits it: camera 8-14 ms, pose 5-7 ms, particles 2.5-4.8 ms.
2. A queued submission thread like the engine's (D228 parity), which would be worth about TF2's 3.6 ms tier0 thread.
3. The viewer's 2-core loss: what the managed helper thread is, and whether the D3D11 driver thread (13-25%) is fighting the main
   thread.
