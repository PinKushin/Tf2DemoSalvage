# Measurement 2026-10-25: instance matrices written in place, one pool per list (B585, second attempt)

**Status: written and committed before the run.** Sections above `## Result` are fixed from here; deviations go under Result.

## Observation

The first attempt (`94217782`, reverted `8b839017`) cached a matrix per entity and compared transforms; its own timer
`place … lookups = matrix` doubled 0.011 → 0.021 ms (measurements/2026-10-24-b586-b585-report-guard-and-matrices.md).
The engine does no compare: `C_BaseAnimating::InternalDrawModel` builds the model-to-world matrix into a stack
`ClientModelRenderInfo_t` every draw (`c_baseanimating.cpp:3464`, `AngleMatrix` at `:3491`), and the renderables list
holds only pointers and handles (`clientleafsystem.h:58-67`, `CEntry`), taken from a fixed-size allocator
(`DECLARE_FIXEDSIZE_ALLOCATOR`, `:50`; `new` per view at `viewrender.cpp:3411`). The new build (`4c7f98a9`) writes each
instance's matrix into a preallocated slot owned by its instance list (`InstanceMatrices`), no compare.

## Question

How much do `place … matrix`, allocated MB a frame, gc pause ms a frame, gen0 collections and frame mean move on f12 gummo
first person and the empty view?

## Prediction

- `matrix` falls below A's 0.011 ms (a 16-float write, no allocation). Falsified if it rises.
- Allocation falls by ~0.02 MB a frame (246 × 88 B, *arithmetic*) — under the 0.09 MB same-build spread, so a null on
  allocation, gc and frame is the likely outcome. Falsified if allocation rises.

## Method

(`D:/measure-f12/b585-pool-after/`). Interleaved A B B A A B per subject (three each), 60 s each, one viewer at a time
through `run-exclusive.ps1`, started only on the lead's go and with no other `tf2demoview`/measure process
(`Get-CimInstance Win32_Process`), three CPU samples under 25% before each:

- gummo: `TF2VIEW_AUTOPLAY=1 TF2VIEW_VIEWPORT_SIZE=1280x720 <exe> D:/measure-f12/f12.dem --tick 30000 --spectate gummo
  --first-person --measure 60 +fps_max 0`
- empty: `TF2VIEW_AUTOPLAY=1 TF2VIEW_VIEWPORT_SIZE=1280x720 TF2VIEW_CAMERA="1613 -2821 154 89 0" <exe>
  D:/measure-f12/f12.dem --tick 30000 --measure 60 +fps_max 0`

Safety: one B run gummo with `+mat_queue_mode 2` and `TF2VIEW_QUEUE_VERIFY=1`.

## Verdict

**The engine's shape wins its own stage and nothing else.** `matrix` falls by ~0.005 ms, which is under the 0.01 ms the
owner counts. Frame, allocation, gc and gen0 don't separate from the spread. The 1.2 MB a frame and 0.2 ms of gc
are elsewhere: the matrices were ~22 KB of it (*arithmetic*). Kept because it is the engine's shape at no cost, unlike
the first attempt, which doubled the same timer.

Against the Prediction. Confirmed: `matrix` fell (A 0.0136-0.0165, B 0.0089-0.0120 ms in this grid, ranges separate), and
allocation did not rise beyond the spread, with the null on allocation, gc and frame that the prediction called likely. One
limit on the first line: the prediction named A's 0.011 ms from the earlier record, and this grid's A reads higher than that,
so the claim holds against this grid's A, and B's top run (0.0120) is above 0.011.

Verdict extended 2026-10-29 after the fact from the Result above; the run itself was not repeated.
