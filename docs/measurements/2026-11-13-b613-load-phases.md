# B613: where the f12 load's silent stretch goes, phase by phase

## Observation

B613 (`docs/RISKS.md`, 2026-10-30): on `demostf-cp_process_f12-2026-08-08-2207.dem` the viewer's log printed
`[demo] cp_process_f12 … protocol 24` and then nothing for about 168 s before proceeding. That figure was read from the
logs of other agents' `--measure` runs, not timed for its own sake. Load-cost fixes have landed since (B667's
displacement sweep, B666's light slots), so whether it still holds on `main` is not known.

## Question

On current `main`, how long does each phase of the f12 load take, from process start to the first measured frame:
the demo decode (the position timeline and its own columns), the map read, the model and sound precache, and the
apply? Is one phase dominant, and is it our own waste?

## Method

Debug build of `tf2demoview` (what the owner runs, D176), built in the same command, under the machine-wide lock:

```
MSBUILDDISABLENODEREUSE=1 dotnet build managed/Tf2DemoSalvage.Viewer3D -c Debug && \
TF2VIEW_AUTOPLAY=1 pwsh C:/Users/pinku/source/repos/PinKushin/run-exclusive.ps1 -TimeoutMinutes 60 \
  managed/Tf2DemoSalvage.Viewer3D/bin/Debug/net10.0-windows/tf2demoview.exe \
  C:/Users/pinku/source/repos/PinKushin/Tf2DemoSalvage/tools/corpus/local/demostf-cp_process_f12-2026-08-08-2207.dem \
  --tick 20000 --measure 5
```

The phase times are the viewer's own `LoggerTiming.Time` lines and the `timeline … ms = commands …` line that
`DecodedDemo.Read` prints, read from stdout after the process exits (the log is buffered). The wall clock around the
whole command is taken with `date` before and after, as a total to set the phases against.

Then, for whichever phase dominates, a CPU sample of the decode alone, off the desktop: the `timeline-cost` probe (Debug,
the build the viewer above ran) under `dotnet-trace collect`, read with the `cpu-trace` probe over the whole build. The
probe prints the same carried `TimelinePhases` columns, including `frames`, which the viewer's log line folds into
`rest`:

```
dotnet build tools/Tf2DemoSalvage.Probe -c Debug && \
pwsh C:/Users/pinku/source/repos/PinKushin/run-exclusive.ps1 -Shared -TimeoutMinutes 60 dotnet-trace collect \
  --output <scratch>/f12-timeline.nettrace -- tools/Tf2DemoSalvage.Probe/bin/Debug/net10.0/Tf2DemoSalvage.Probe.exe \
  timeline-cost <f12>
dotnet run --project tools/Tf2DemoSalvage.Probe -c Release -- cpu-trace <scratch>/f12-timeline.nettrace 0 9999 <thread> 60
```

## Control

The phases are carried from the code that ran them, not recomputed. The sum of the logged phases is compared with the
wall clock around the command: a large unexplained remainder means a phase is not timed and the list is incomplete.

## Environment

The owner's machine, branch `fix/b613-silent-load`. Before: `88e0b98fe` (main `945b5f342` plus this file), Debug viewer
alone under `run-exclusive.ps1` after waiting about 16 minutes for another agent's f12 runs; Debug probe under the trace
as a `-Shared` holder. After: the working tree of the commit that adds `DecodeProgressLog` (it changes only what is
logged), Debug viewer under the lock. CPU load from other agents was not sampled; other agents were building and running
in the same hour, which is the likeliest reading of the spread below (*interpolated*).

## Verdict

**The silent stretch is the position timeline's decode, and it still holds on current `main` at more than the filed
168 s:** 208-252 s in the viewer (Debug), 204 s in the probe, 83% of the 302 s from process start to the first frame of
the before-run. The map, models, sounds and apply after it are 48 s together, each with its own log line.

**No single step inside the decode is our own dominant waste.** Entities, the per-frame player build and sampling are
77, 79 and 45 s of the probe's 204 s. The sample's largest spots (`RecordProp`'s direct copy 12%, `CarriedItems` 16%,
`SoundscapeIndex` 6%) are each within the 208-252-151 s spread between three runs of one demo on one day, so no
before-and-after from single runs could show a fix of one; none was made here.

**The window was never silent** (the overlay shows the decode's percentage); the log was. After the change the log
reports each tenth of the decode, the longest gap falling from 252.4 s to 20.2 s.
